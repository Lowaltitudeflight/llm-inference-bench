我给 8 卡 72B 写了个开源压测工具：聊聊 LLM 推理压测里最容易写错的 5 件事

项目地址：https://github.com/yangchuan665/llm-inference-bench

这是一个多引擎（vLLM / Ollama）、多量化等级（FP16 / INT8 / AWQ）的大模型推理压测与评测平台。313 个单元测试，无 GPU 也能跑通全链路。


【起因】

我在实习时做过 8 卡 RTX PRO 5000 部署 Qwen2.5-72B 的活儿。部署本身不难，难的是——部署完之后，怎么证明它跑得好。

客户会问：

· 这套配置能扛多少并发？
· 用户体感快不快？
· 延迟长尾会不会爆？
· 换量化能省多少显存、掉多少性能？

我当时是手写脚本凑的答案。后来发现，这些脚本里的指标算法几乎每一处都踩了坑——不是代码报错，而是悄无声息地算错，然后你把错误结论交出去了。

所以我把这套东西重写成了一个开源工具，并且刻意给每个指标口径写了测试。写完测试的过程中，真的抓出了 5 个 bug。

这篇文章不讲怎么用（README 里有），只讲那些容易写错的地方。如果你自己写压测脚本，这几点大概率能帮你省点事。


一、TTFT 不能用「响应时间」，必须用「首个内容分片」

TTFT（Time To First Token，首包延迟）在流式场景下是唯一有意义的体感指标。用户不会关心「整个回答花了几秒」，他在意的是「多久开始出字」。

最常见的错误是这么测：

    start = time.time()
    resp = client.chat.completions.create(...)   # 非流式
    ttft = time.time() - start                   # 这是错的

这测出来的是总耗时，不是首包延迟。

更隐蔽的一种错误是用流式，但把 TTFT 记成「收到 HTTP 200 的时刻」：

    resp = client.chat.completions.create(..., stream=True)
    ttft = time.time() - start      # 这也是错的
    for chunk in resp:              # 真正的首 token 在这里才到
        ...

HTTP 200 返回的时候，模型一个字都还没出。中间还隔着两段：

    请求发出 --+-- 排队 --+-- prefill --+-- 首 token --+-- 后续 token...
               |          |             |              |
               +----------+-------------+              +-- 生成阶段
                  这一段才是 TTFT 要测的

正确做法是在流式解析循环里，等第一个 delta.content 非空的分片到达时打点：

    for chunk in resp:
        delta = chunk.choices[0].delta
        if delta.content:                      # 第一个有内容的块
            if ttft is None:
                ttft = time.perf_counter() - start
            # ... 后续累加生成阶段耗时

顺便一提，vLLM 和 Ollama 都支持 stream_options={"include_usage": True}，能让服务端在最后一个分片里返回准确的 token 统计，比客户端自己数更可靠。


二、TPOT 的分母要减 1

TPOT（Time Per Output Token）衡量解码速度。直觉上会这么算：

    tpot = 总耗时 / 输出token数      # 错的

问题在于：第一个 token 的等待时间已经算进 TTFT 了。如果分母用全部 token 数，等于把 prefill（处理输入的全部 token）的时间也摊到了每个解码 token 上，结果会系统性偏大——看起来模型比实际慢。

正确写法：

    tpot = 生成阶段耗时 / (输出token数 - 1)

这个坑很隐蔽，因为量级上看不出问题（差一个 token 而已），但当你拿 TPOT 去对比不同量化配置的优劣时，这个偏差会污染结论。

边界情况：输出只有 1 个 token 时分母为 0。我在代码里直接返回 None 而不是让它崩掉——压测跑一半崩了比数据缺失更糟。

    if self.generation_time is None or self.output_tokens <= 1:
        return None
    return self.generation_time / (self.output_tokens - 1)


三、吞吐不能算输入 token，也不能用「耗时求和」

两个容易同时踩的坑。

坑 1：把输入 token 算进吞吐

    吞吐 = (输入token + 输出token) / 耗时      # 错的

prefill 是并行计算，产出的是 KV cache，不是用户可见的输出。把 prompt token 算进去，吞吐会虚高，而且随 prompt 长度剧烈波动——换个长 prompt 数字就变了，没法做横向对比。

坑 2：用各请求耗时求和当分母

    吞吐 = 总输出token / sum(每个请求的耗时)      # 错的

并发请求是时间上重叠的。32 个并发请求各花 3 秒，总耗时不是 96 秒，而是大约 3 秒。用求和会让吞吐被严重低估。

正确做法是用墙钟时间（wall clock），而且要用不受系统时钟调整影响的计时器：

    start = time.perf_counter()
    # ... 所有并发请求跑完 ...
    wall = time.perf_counter() - start
    吞吐 = 总输出token / wall


四、多卡显存峰值：取各卡最大值会少报 N 倍

这条是我写测试时才发现的，而且是逻辑错误，不是笔误。

监控多卡显存时，很容易这么写：

    峰值 = max(每张卡各自的峰值)      # 错的

看起来合理，实际上错得离谱。假设 8 张卡，每张峰值占用 60 GiB：

· max(各卡峰值) → 60 GiB （少报 8 倍）
· max(各时刻各卡之和) → 480 GiB （正确）

真实占用是 480 GiB（8 张卡同时各占 60 GiB），而上面的写法只报 60 GiB——客户按这个数去配机器，直接爆显存。

正确做法是先把所有卡按时间戳对齐求和，再取时序最大值：

    by_t = {}
    for s in samples:
        if s.memory_used_mib is None:
            continue
        by_t[s.t] = by_t.get(s.t, 0.0) + s.memory_used_mib

    peak = max(by_t.values())

注意不能简单地「把所有卡的峰值相加」——某些时刻可能只有部分卡在忙，那样会高估。

我给这个场景专门写了个回归测试守着：

    def test_multi_gpu_peak_not_underreported():
        # 8 张卡 x 60000 MiB
        # 全局峰值必须是 480000，而不是 60000
        ...
        assert curve["peak_memory_used_mib"] == 480000


五、分位数别用「最接近的样本」，小样本下会退化成最大值

延迟的 P99 是判断长尾的关键。但分位数的算法有好几种，选错了在小样本下会失真。

容易这么写：

    def percentile(values, p):
        ordered = sorted(values)
        idx = int(len(ordered) * p / 100)      # 小样本下会取到极端值
        return ordered[idx]

问题在压测场景下很实际：并发 32、每档只跑 32 个请求时，这个算法算出的 P99 往往直接等于最大值，失去统计意义。

更稳的是线性插值（和 NumPy 默认的 linear 方法一致）：

    rank = (p / 100) * (len(ordered) - 1)
    lo = int(math.floor(rank))
    hi = min(lo + 1, len(ordered) - 1)
    frac = rank - lo
    return ordered[lo] + (ordered[hi] - ordered[lo]) * frac

这样 P99 会落在两个样本之间，不会因为样本少就退化成极值。


用真实数据看看这些指标长什么样

下面是这个工具在 mock 引擎上跑出的一组数据。

（重要：mock 引擎的延迟是模拟值，只用于演示报告格式，不能用来推断真实硬件性能。）

FP16 配置，并发梯度 1 到 32（完整表格建议截图，这里按行列出）：

【并发 1】吞吐 82.9 tok/s ｜ TTFT均值 93.02 ms ｜ TPOT 10.75 ms ｜ P50 769.96 ms ｜ P95 769.96 ms ｜ P99 769.96 ms
【并发 2】吞吐 156.5 tok/s ｜ TTFT均值 107.09 ms ｜ TPOT 10.74 ms ｜ P50 783.62 ms ｜ P95 812.34 ms ｜ P99 814.90 ms
【并发 4】吞吐 301.9 tok/s ｜ TTFT均值 123.92 ms ｜ TPOT 10.78 ms ｜ P50 810.50 ms ｜ P95 834.16 ms ｜ P99 835.97 ms
【并发 8】吞吐 549.1 tok/s ｜ TTFT均值 159.28 ms ｜ TPOT 10.77 ms ｜ P50 842.47 ms ｜ P95 890.66 ms ｜ P99 894.30 ms
【并发 16】吞吐 1054.1 tok/s ｜ TTFT均值 189.60 ms ｜ TPOT 10.77 ms ｜ P50 880.22 ms ｜ P95 913.93 ms ｜ P99 916.84 ms
【并发 32】吞吐 1911.0 tok/s ｜ TTFT均值 226.86 ms ｜ TPOT 10.77 ms ｜ P50 919.99 ms ｜ P95 955.53 ms ｜ P99 957.52 ms

几个值得注意的地方。

吞吐基本随并发线性增长（82.9 到 1911，约 23 倍），说明还没到饱和拐点——真实的 8 卡 72B 通常会更早出现平台期。

TTFT 随并发明显上升（93 ms 到 227 ms，涨了 2.4 倍），这是排队导致的。吞吐涨了，但单个用户的等待变长了——这就是为什么吞吐和延迟必须成对看。

TPOT 几乎不变（10.74 到 10.78 ms），符合预期：解码阶段是逐 token 进行的，并发增加主要影响排队和调度，对单 token 生成速度影响不大（前提是显存没打满）。

再看量化对比：

FP16（基线）  峰值吞吐 1911.0 tok/s   相对基线 1.000x
AWQ           峰值吞吐 1874.1 tok/s   相对基线 0.981x

在 mock 环境里 AWQ 略慢于 FP16（模拟了反量化开销），报告如实呈现，没有为了让量化「看起来更好」而挑数据。

这也是我做报告时的一条原则：只陈述可验证的事实，比如「awq 峰值 1874.1 tokens/s，比最优低 2.0%」，而不是写「awq 性能优异，是部署首选」——后者是价值判断，不是数据。


还有就是：报告得能在隔离内网打开

私有化交付场景经常遇到物理隔离的内网。我一开始用常规方式生成 HTML 报告（引入绘图库、CDN 加载字体），结果拿到现场打开一片白。

所以报告改成了完全自包含：内联 SVG 手绘图表、零外部引用、零 script 标签。

    size: 28165 bytes
    内联 SVG 数: 4
    script 标签: 0
    外部引用: 无

测试里有一条断言专门守着这个特性——防止以后有人「顺手」引入一个绘图库把报告搞坏。


关于测试

这个项目有 313 个单元测试，约 7 秒跑完，而且不依赖真实网络、真实 GPU、真实模型，所以能在任何 CI 上跑。

其中内置了一个 OpenAI 兼容的 mock 引擎，模拟了排队延迟（TTFT 随并发以 log2 上升），让整条链路能在没有显卡的机器上验证。这对协作很关键——总不能要求每个贡献者都有一台 8 卡机。

前面说的 5 个 bug，全是在写测试的过程中发现的。我现在的体会是：指标类代码一定要写测试，因为它算错的时候不报错，只是安静地给你一个错误的数。


小结

如果你也在写 LLM 压测脚本，这 5 条可以拿去自查：

1. TTFT 记成响应时间 → 流式下等首个有内容的分片
2. TPOT 分母用全部 token 数 → 分母减 1（首 token 已计入 TTFT）
3. 吞吐算上输入 token / 耗时求和 → 只算输出 token，分母用墙钟时间
4. 多卡显存取各卡最大值 → 按时间戳求和后取时序峰值
5. 分位数取最近样本 → 线性插值
