# 压测方法论

这份文档说明本工具的各项指标**怎么测、为什么这么测、什么情况下会测不准**。
在客户现场被追问「你这个数是怎么来的」时，这里应该是能直接回答的内容。

---

## 一、先明确：压测要回答什么问题

压测常见的失败模式是「跑了一堆数但说明不了任何事」。所以先锁定问题：

| 问题 | 对应指标 | 采集方式 |
| --- | --- | --- |
| 单用户体感快不快？ | TTFT | 流式首内容分片时间 |
| 出字速度快不快？ | TPOT | 生成耗时 / (输出 token − 1) |
| 单请求完整要多久？ | 端到端延迟 | 请求发出 → 最后分片 |
| 系统整体能出多少字？ | 吞吐 tokens/s | 总输出 token / 墙钟时间 |
| 并发上来会不会崩？ | 失败率、P99 | 并发梯度扫描 |
| 长尾有多糟？ | P95 / P99 | 分位数统计 |
| 显存吃多少？ | 峰值显存 | nvidia-smi 轮询 |
| 换量化值不值？ | 吞吐/显存比 | 横向对比矩阵 |

**吞吐和延迟是一对矛盾量。** 只看吞吐会选出「高并发下延迟爆表」的配置，
只看延迟会选出「单请求很快但并发一上来就堵」的配置。必须成对呈现。

## 二、关键指标的精确定义

### 2.1 TTFT（Time To First Token，首包延迟）

**定义**：从发出请求到客户端收到**第一个携带内容的分片**的时间。

**为什么不能用「HTTP 200 到达时间」**：服务端返回响应头之后，还要经历
请求排队、prefill（处理输入的全部 token）、生成第一个 token 三个阶段，
这段时间才是用户真正感知的「等待」。用响应头时间会严重低估体感延迟。

**为什么必须流式**：非流式请求只有一个总耗时，首包延迟这个量根本不存在。
本工具强制 `stream=true`。

**测量实现**：在 SSE 解析循环中，首个 `delta.content` 非空的分片到达时打点。

```
请求发出 ──┬─ 排队 ─┬─ prefill ─┬─ 首 token ──┬─ 后续 token...
           │        │           │             │
           └────────┴───────────┘             │
              ← TTFT 测的就是这段 →            └ 生成阶段
```

### 2.2 TPOT（Time Per Output Token）

**定义**：`生成总耗时 / (输出 token 数 − 1)`

**为什么要减 1**：第一个 token 的等待时间已经算进 TTFT 了。
如果按 `总耗时 / 输出token数` 计算，等于把 prefill 时间摊到了每个 token 上，
会系统性低估解码速度。这是很多自研压测脚本会写错的地方。

**边界情况**：输出只有 1 个 token 时分母为 0，此时 TPOT 无意义，记为 `None`。
`tests/test_stats.py` 里有专门的用例守着。

### 2.3 吞吐（Throughput）

**定义**：`总输出 token 数 / 墙钟时间`，单位 tokens/s。

**两个易踩的坑**：

1. **输入 token 不能算进吞吐**。prefill 是并行计算，产出的是 KV cache 而不是
   用户可见的输出。把 prompt token 算进去会让吞吐虚高，且随 prompt 长度剧烈变化。
   本工具统计的是 `output_tokens`。

2. **计时要用墙钟，不能用各请求耗时求和**。并发请求是重叠的，
   求和会得到远大于实际墙钟的数，吞吐被严重低估。

**单位说明**：报告中出现的 `tokens/s` 均为**输出吞吐**。

### 2.4 分位数（P50 / P95 / P99）

**定义**：线性插值法。对有序样本 `x[0..n-1]`，第 p 分位数的位置为
`(n-1) * p`，落在两个样本之间时按距离线性插值。

**为什么不用「最接近的样本」**：并发 32、每档 32 个请求时，
P99 若取最近样本会直接退化成「最大值」，失去统计意义。
线性插值（与 NumPy 默认行为一致）在小样本下更稳健。

**为什么一定要看 P99**：均值会掩盖长尾。真实场景里用户抱怨的从来不是
「平均要等 200ms」，而是「偶尔要等 3 秒」。P99 就是那个「偶尔」。

## 三、并发梯度扫描

### 为什么是梯度而不是单一并发

单点压测只能告诉你「这个并发下能跑」。梯度扫描能找出**饱和拐点** ——
吞吐不再随并发增长的那个点。这才是容量规划的依据。

推荐的档位序列：`1, 2, 4, 8, 16, 32, 64`
（2 的幂次覆盖范围广，且相邻档位比值恒定，曲线在对数轴上均匀分布）

### 每档请求数的选择

太少则统计不稳定，太多则耗时过长。经验规则：

- 并发 ≤ 8：每档至少 16 个请求
- 并发 ≥ 16：每档请求数 ≥ 并发数的 2~4 倍

原因是高并发档位下单个请求的耗时会显著变长，请求数不够的话，
整档的采样窗口太短，容易被启动时的瞬时抖动主导。

### 曲线形状的解读

```
吞吐
  │         ╭──────────────  ← 饱和平台：再加并发也不会更快
  │      ╭──╯
  │   ╭──╯
  │ ╭─╯
  └─┴────┴────┴────┴────┴──→ 并发
    1    4    8   16   32

TTFT
  │                    ╭───  ← 排队恶化：请求在队列里干等
  │              ╭─────╯
  │        ╭─────╯
  │  ╭─────╯
  └──┴────┴────┴────┴────┴──→ 并发
     1    4    8   16   32
```

**健康的曲线**：吞吐爬升后进入平台，同时 TTFT 缓慢上升。
**危险的曲线**：吞吐在某个点**掉头向下**，同时 P99 陡增 ——
说明已经过载，请求开始超时重试，实际有效吞吐反而下降。

报告里的「饱和拐点」就是吞吐曲线上的峰值点。

## 四、预热为什么必须剔除

首次请求会触发一系列一次性开销：

- CUDA context 初始化与 kernel 首次编译（JIT）
- 显存池首次分配（PagedAttention 的 block pool 建立）
- 连接建立与 TLS 握手（如果走 HTTPS）
- 模型权重首次从内存换入

这些开销在稳态下不再出现。如果不剔除，并发=1 的档位会被首请求严重拉偏 ——
而这种偏差往往表现为「延迟高得离谱」，进而误导出「低并发性能差」的错误结论。

本工具默认每档先跑 2 个预热请求，**其结果不进入统计**。

## 五、测量环境要求

### 5.1 必须做的

| 项 | 要求 | 原因 |
| --- | --- | --- |
| 目标引擎 | 独立进程、已完成模型加载 | 避免把加载时间算进压测 |
| 压测客户端 | 与引擎不同机（或至少不同 GPU） | 排除客户端抢占资源 |
| 网络 | 同交换机、无跨机房 | 网络抖动会污染尾延迟 |
| 采样前 | 清空其他 GPU 任务 | 显存与算力被争抢会失真 |
| 环境温度 | 稳定 | 温度过高触发降频，吞吐不可复现 |

### 5.2 代理问题（Windows 常见）

系统代理会拦截 `127.0.0.1` 请求，表现为莫名其妙的
`502 upstream connect failed`。必须先排除本地地址：

```bash
export NO_PROXY="127.0.0.1,localhost"
export no_proxy="127.0.0.1,localhost"
```

### 5.3 结果可复现性

**同一配置重复跑，吞吐波动通常有 3~8%。** 这是正常的，来源包括：
GPU 温度漂移、其他进程干扰、采样窗口位置差异。

因此：

- 不要用「吞吐高 2%」来论证配置优劣 —— 这在噪声范围内
- 对比不同配置时，务必保证并发档位、`max_tokens`、prompt 完全一致
- 关键结论建议重复跑 3 次取中位数

报告中的量化对比会标注相对比值，但请结合上述噪声范围解读。

## 六、量化等级横向对比

### 六点一、基线怎么定

FP16 / BF16 是未经压缩的原始精度，作为基线。
`BASELINE_QUANTS = {fp16, bf16, float16, bfloat16, none, unknown}`

### 6.2 要看的三个量

| 指标 | 含义 | 期望方向 |
| --- | --- | --- |
| 吞吐相对比 | `本配置吞吐 / 基线吞吐` | 越接近 1 越好 |
| TTFT 变化 | 相对基线的百分比变化 | 通常持平或略降 |
| 显存比 | `本配置显存 / 基线显存` | 越小越好 |
| **每 GiB 显存吞吐** | `吞吐 / 显存占用(GiB)` | **越大越好 ← 性价比核心** |

**每 GiB 显存吞吐**是选型的关键指标。INT8/AWQ 相比 FP16 通常能省 40~50% 显存，
吞吐损失在 5~15% 之间。如果省下的显存能换来更大的 batch size 或更长的上下文，
净收益可能为正 —— 这就是「量化值不值」的量化依据。

### 6.3 结论的措辞原则

本工具只陈述可验证的事实：

> ✅ `Qwen2.5-72B-AWQ @ awq 峰值 1874.1 tokens/s，比最优低 2.0%`
> ✅ `awq 显存占用为基线的 0.52 倍，每 GiB 吞吐提升 1.89 倍`
> ❌ `awq 量化性能优异，是部署首选`（无数据支撑的价值判断）

在 mock 环境里 AWQ 本来就比 FP16 略慢（模拟了反量化开销），
报告如实呈现，不为了「量化看起来更好」而挑数据。

## 七、显存测量

### 7.1 采样方式

后台线程轮询 `nvidia-smi --query-gpu=memory.used,...`，默认间隔见 `MonitorConfig`。
主流程零阻塞。

### 7.2 峰值必须按时序求和（多卡）

**这是最容易写错的地方。**

假设 8 张卡，每张峰值占用 60 GiB：

| 算法 | 结果 | 是否正确 |
| --- | --- | --- |
| `max(各卡峰值)` | 60 GiB | ❌ 少报 8 倍 |
| `max(各时刻各卡之和)` | 480 GiB | ✅ |

某些时刻可能只有部分卡在忙，所以不能简单用「所有卡峰值相加」，
必须**先按时间戳对齐求和，再取时序最大值**。

`tests/test_gpu_monitor.py::test_multi_gpu_peak_not_underreported`
用 8 × 60000 MiB 的场景守着这条。

### 7.3 分阶段窗口对齐

压测是多档并发的，每档的显存占用不同（取决于当时的 KV cache 规模）。
`LoadRunner` 会记录每档的采样起止索引，`vram_curve()` 按索引切分，
得到「每档的显存峰值」—— 这才能看出显存随并发增长的斜率。

### 7.4 局限性

- 采到的是**瞬时快照**，真正的峰值可能出现在两次采样之间（建议采样间隔 ≤ 0.5s）
- 只有 NVIDIA 平台；其他平台静默降级为「无显存数据」，不影响压测本身
- MIG 实例下 `nvidia-smi` 的报数口径与物理卡不同，需自行折算

## 八、Prometheus 指标口径

### 为什么不能用默认分桶

`prometheus_client` 的默认直方图分桶是
`.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10`（秒）。

LLM 的 TTFT 在 50~500ms 量级，会全部挤在 `.05` 和 `.1` 两个桶里 ——
P99 估计值基本等于桶边界，毫无分辨力。因此本工具为
TTFT / TPOT / 端到端延迟分别定制了分桶（见 `metrics/prometheus.py`）。

### 直方图是累计值

`_bucket` 系列从服务启动起持续累加。跑第二次压测时，P99 会**混入第一次的数据**。
需要干净的观测窗口时，重启服务。

### 运行元信息要一次性写入

`Info.info()` 每次调用会**整体替换**标签集合。写多个字段必须：

```python
run_info.clear()
run_info.info({"run_id": ..., "engine": ..., "model": ..., "status": ...})
```

逐字段调用会导致最后只剩一个字段（这是本版本修掉的一个真实缺陷）。

## 九、常见坑点速查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 所有请求都失败，但报告全是 N/A | CLI 静默退出 0（已修复） | 看 stderr 的 ❌ 失败块 |
| 本地请求 502 | 系统代理劫持 localhost | 设 `NO_PROXY=127.0.0.1,localhost` |
| 首档延迟异常高 | 预热未生效 | 增加 `--warmup` |
| 吞吐随并发下降 | 过载，请求开始超时 | 降低档位上限，看失败率 |
| 显存数据为空 | 无 nvidia-smi / 非 NVIDIA | 正常降级，不影响压测 |
| 多卡显存数看着偏小 | 峰值算法取单卡最大值 | 已修复；确认用 0.1.0+ |
| 两次运行结果差很多 | 温度/干扰导致（3~8% 正常） | 重复 3 次取中位数 |
| 量化对比只有 1 组 | 两次运行落在不同 run 目录 | 用同一 `--run-id` |
| HTML 报告白屏 | 报告被改成了引用外部资源 | 保持自包含，测试有断言守着 |
| Prometheus P99 一直不变 | 直方图累计，混入历史数据 | 重启服务 |

## 十、一次完整压测的推荐流程

```bash
# 0. 排除代理干扰
export NO_PROXY="127.0.0.1,localhost" no_proxy="127.0.0.1,localhost"

# 1. 先探测引擎与模型
python scripts/run_bench.py --check \
    --base-url http://127.0.0.1:8000/v1 --model Qwen2.5-72B-Instruct

# 2. 全链路试跑（小 max_tokens，确认没有配置问题）
python scripts/run_bench.py --base-url http://127.0.0.1:8000/v1 \
    --model Qwen2.5-72B-Instruct --quant fp16 \
    --levels 1,4 --max-tokens 32 --warmup 2 --output-dir /tmp/smoke

# 3. 正式扫描（相同输出长度的配置才能横向比较）
python scripts/run_bench.py --base-url http://127.0.0.1:8000/v1 \
    --model Qwen2.5-72B-Instruct --quant fp16 \
    --levels 1,2,4,8,16,32,64 --max-tokens 512 \
    --run-id quant-72b --output-dir data/results

# 4. 换量化配置，用同一 run-id 以便对比
python scripts/run_bench.py --base-url http://127.0.0.1:8000/v1 \
    --model Qwen2.5-72B-AWQ --quant awq \
    --levels 1,2,4,8,16,32,64 --max-tokens 512 \
    --run-id quant-72b --output-dir data/results

# 5. 从结果重新出报告（可反复调报告模板而不重跑压测）
python scripts/run_bench.py --report-only --from-results data/results/quant-72b

# 6. 起服务 + 监控栈，持续观测
python scripts/serve.py --port 8090
cd deploy && docker compose up -d
```

**关键：第 3、4 步的并发档位、`max_tokens`、prompt 必须完全一致**，
否则横向对比没有意义。报告会校验并发档位取交集，但输出长度无法校验 ——
这需要人工保证。
